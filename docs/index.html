01项目概览

mybook 是一个以「图文 / 视频笔记」为核心内容的社区平台，业务形态对标小红书： 用户注册登录后发布笔记，可以关注其他用户、浏览关注流与笔记详情。 工程上采用 Spring Cloud 微服务架构，按业务域拆分服务，并在若干关键链路上 引入了分布式 ID、多级缓存、消息削峰与异构存储。

设计意图

  • 契约与实现解耦：调用方只依赖 -api 这个薄 JAR，不需要知道对方如何实现，也不可能反向依赖到对方的 biz。
  • 依赖单向：auth → user-api、note → user-api / kv-api / id-api， 被依赖方不感知调用方，天然避免循环依赖。
  • 服务名集中定义：ApiConstants.SERVER_NAME = "mybook-kv"， 与 Nacos 中 spring.application.name 对齐，改一处即可。
  • Feign 客户端统一扫描：启动类通过 @EnableFeignClients(basePackages = "com.mybook.mybook") 跨模块扫描， 因为各服务包名都收拢在 com.mybook.mybook.* 下。

03数据模型（内容设计）

数据模型按业务域分库表设计，DDL 集中在 sqls/ddl.sql，初始化数据在 sqls/insert.sql。 共 16 张 MySQL 表（业务库 mybook 15 张 + 发号器库 leaf 1 张）， 另有 1 张 Cassandra 宽表承载笔记正文。

建模范式与约定

统一字段约定

  • 主键：id bigint unsigned auto_increment，InnoDB + BTREE。
  • 逻辑删除：is_deleted bit(1) default b'0'，不物理删除业务数据。
  • 审计字段：create_time / update_time 均默认 CURRENT_TIMESTAMP。
  • 字符集：utf8mb4 / utf8mb4_unicode_ci，支持 emoji（社区内容刚需）。
  • 枚举落地：状态类字段用 tinyint 存码值，Java 侧由 NoteStatusEnum 等枚举收口，避免魔法数字散落。

索引即业务约束

  • t_user：uk_mybook_id、uk_phone —— 账号唯一性由数据库兜底。
  • t_following：uk_user_id_following_user_id —— 用联合唯一索引实现关注幂等， 重复消费消息不会产生重复关系。
  • t_note_like / t_note_collection：uk_user_id_note_id —— 一人对一篇笔记只能有一条点赞 / 收藏记录，状态用 status 位切换而非插入新行。
  • t_note：idx_creator_id、idx_topic_id、idx_status —— 覆盖「查某人的笔记」「查某话题下的笔记」「过滤待审核 / 已下架」三类主查询。

统一响应契约

Response<T>（framework/mybook-common）

{
  "success": true,
  "message": null,
  "errorCode": null,
  "data": { ... }
}

失败时 success=false，并带上 errorCode 与 message。 所有 Controller 无论成功失败都返回 HTTP 200，业务结果由 success 表达 —— 让客户端只需一套解析逻辑。

PageResponse<T> 扩展分页字段

{
  "success": true,
  "data": [ ... ],
  "pageNo": 1,
  "pageSize": 10,
  "totalCount": 3,
  "totalPage": 1
}

pageSize 固定 10，totalPage 由 PageResponse.success() 内部按 (totalCount + pageSize - 1) / pageSize 计算，调用方无需自行推导。

错误码分段

每个服务用独立前缀 + 分段定义错误码，便于日志定位与客户端分类处理，统一实现 BaseExceptionInterface 后由 BizException 承载。

服务前缀段位含义示例
KV-10000+系统级错误KV-10000 系统异常、KV-10001 参数错误
20000+业务级错误KV-20000 该笔记内容不存在
其他服务x10000+系统级错误ResponseCodeEnum.SYSTEM_ERROR
x20000+业务级错误如笔记不存在、非发布者不可操作、关注对象不存在等

每个 -biz 模块都有自己的 enums/ResponseCodeEnum 与 exception/GlobalExceptionHandler，后者统一捕获 BizException、MethodArgumentNotValidException（参数校验）、 IllegalArgumentException（Guava Preconditions）与兜底 Exception。

05核心流程（内容设计）

以下 6 条流程覆盖了系统的主要写入与读取路径，也是设计原理最集中的地方。

时序

1
下发验证码 POST /auth/verification/code/send
先 hasKey 判断是否已发送（存在即视为频繁，抛 VERIFICATION_CODE_SEND_FREQUENTLY）； 生成 6 位随机数字，写入 Redis verification.code.{phone}，TTL 3 分钟。
2
提交登录 POST /auth/login
LoginTypeEnum 分流：1 验证码登录、2 账号密码登录。
3
验证码分支
比对 Redis 中的验证码；通过后调用 userRpcService.registerUser(phone) —— 登录即注册，未注册用户在此自动建号。
4
密码分支
findByPhone 取回 BCrypt 密文，passwordEncoder.matches() 校验。
5
签发令牌
StpUtil.login(userId) → StpUtil.getTokenInfo().tokenValue 作为 Response.data 返回。token 风格 uuid，有效期 30 天，允许多端并存且共用同一 token。

设计要点

  • 验证码即注册凭证：省掉独立的注册流程，降低新用户门槛，这是社区产品的常见取舍。
  • 验证码只存 Redis：天然带 TTL，不需要定时清理任务；hasKey 兼作 60s 级频控。
  • 认证与用户资料分离：mybook-auth 不持有用户表，密码规则、用户主数据都归 mybook-user， 认证服务只是「编排者」，未来接入第三方登录时改动面很小。
  • 密码不落明文：PasswordEncoderConfig 提供 BCrypt。

已知待办

  • 两种 ID 策略按业务分工：用户侧标识（mybook_id）需要可读、可从固定值起步， 故用号段；笔记量大且并发生成，故用雪花。见第 07 节。

  • 外部依赖前置校验：creatorId 为空（未登录）在写任何存储之前就抛出，不做无用 IO。

读取路径（三级）

Caffeine 本地缓存  ──miss──▶  Redis  ──miss──▶  MySQL
   ↑ 命中即返回             ↑ 命中则异步回填本地    ↑
   （同进程、纳秒级）        （跨实例共享）       （含并发 RPC 编排）
L1
Caffeine
LOCAL_CACHE.getIfPresent(noteId)；命中后仍需做可见性校验， 因为缓存内容对所有人都一样，而「仅自己可见」的判断依赖当前登录人。
L2

L3

selectByPrimaryKey 查不到 → 异步写入 "null" 短过期占位； 查到后用 CompletableFuture.allOf 并行调用户服务（取头像昵称）与 KV 服务（取正文）。

设计要点

  • 防穿透：不存在的笔记写 "null" 占位，过期 60 + 随机 0~60 秒 —— 短过期既挡住恶意刷不存在 ID 的流量，又不会长期占用内存。
  • 防雪崩：所有过期时间都加随机量（正文 1 天 + 随机 1 天；用户信息同理）， 避免同一时刻批量失效导致数据库被击穿。
  • 并发编排：两次 RPC 无依赖关系，用 CompletableFuture 并行执行， 响应时间从「A + B」降到「max(A, B)」。
  • 回填与返回解耦：写缓存放在异步线程，不阻塞用户响应 —— 代价是存在极短的缓存空窗，对详情页可接受。
  • 可见性校验位置：无论从哪一级缓存命中都要校验，且校验逻辑收敛在 checkNoteVisible() 一处。

对照实现

findNoteDetailWithSync 是一份同步版实现，与异步版并存， 说明这套缓存编排是逐步演进出来的，保留旧实现便于对比验证。

时序（延迟双删 + 广播失效）

1
鉴权
查 t_note；非发布者抛 NOTE_CANT_OPERATE。
2
删元数据 + 回收正文
删除 MySQL 笔记行；若 contentUuid 存在则调 KV 服务删正文。
3
发本地缓存失效消息
TOPIC_DELETE_NOTE_LOCAL_CACHE，延迟级别 1（约 1s）。
4
发 Redis 缓存失效消息
TOPIC_DELAY_DELETE_NOTE_REDIS_CACHE，同样延迟 1s。
5
消费者执行删除
DelayDeleteNoteRedisCacheConsumer 删 Redis； DeleteNoteLocalCacheConsumer 删本地缓存。

为什么是「延迟」双删

  • 删除动作发生在数据库提交之后，此刻可能仍有并发读线程正持有旧值， 并在稍后写回缓存 —— 如果立刻删，这个「脏回填」会留在缓存里。
  • 延迟约 1 秒再删一次，让那批在途读请求的回填动作先落地、再被清掉， 从而把脏数据窗口压到最小。

为什么用 MQ 而不是本地延迟队列

  • 本地缓存是每台实例私有的：Caffeine 只存在于处理该请求的进程内。 用广播型消息让所有实例各自清理，是分布式本地缓存失效的标准做法。
  • RocketMQ 原生支持延迟级别，不引入额外的调度组件；失败还有重试。
  • 服务重启后消息不丢，比进程内的 ScheduledExecutorService 更可靠。

06架构设计原理

这一节回答「为什么这样设计」。每条原理都对应到具体代码，而不是泛泛的架构口号。

原理 1 · 统一入口：把横切关注点全部收敛到网关

鉴权、跨域、身份解析这类「每个服务都要做、但都不该各自实现」的事情，全部由 mybook-gateway 承担，业务服务对此完全无感。

客户端
Authorization:
Bearer <token>
SaReactorFilter 鉴权
拦截 /**，白名单放行 /auth/login、/auth/verification/code/send、/actuator/health
AddUserId2HeaderFilter @Order(-90)
StpUtil.getLoginIdAsLong() 解析 token，把 userId 塞进请求头；未登录则原样放行
业务服务 HeaderUserId2ContextFilter
请求头 → LoginUserContextHolder（TTL），请求结束 finally 中 remove()
下游服务 FeignRequestInterceptor
从 TTL 取出 userId，继续写入下游请求头，身份沿着调用链传递
身份透传链路：token → 网关解析 → 请求头 → ThreadLocal → Feign → 下游服务

为什么让网关解析 token

业务服务只认 userId 请求头，不引入 Sa-Token 依赖、不关心 token 用什么算法签发。 将来换认证方案（JWT / OAuth2），只需改网关一处。 代价：内网服务若被绕过网关直接调用将失去鉴权 —— 因此 kv / oss / id-generator 都不暴露在网关路由中，只在集群内网可达。

为什么要用 TTL 而不是 ThreadLocal

业务里大量使用 threadPoolTaskExecutor.submit(...) 做异步回填。 普通 ThreadLocal 在线程池复用场景下会丢上下文（子线程拿不到 userId， 甚至拿到上一个任务的残留值）。TransmittableThreadLocal 在任务提交时快照、 执行时回放，保证异步链路里 LoginUserContextHolder.getUserId() 依然正确。 MyBookAuthApplication 的 logout() 中特意在异步线程里再取一次 userId 打日志， 就是对这一行为的验证。

CORS 与 Sa-Token 的顺序陷阱

浏览器预检 OPTIONS 请求不带 Authorization，会被 Sa-Token 判为未登录并返回 401， 导致跨域失败。CorsConfig 把 CorsWebFilter 标注为 @Order(Ordered.HIGHEST_PRECEDENCE)，排在 Sa-Token 过滤器之前命中预检并短路返回； 同时 CORS 响应头在进入后续过滤器链前就已写入响应，因此 Sa-Token 抛出的 401 JSON 也带得上该头， 浏览器才能读到错误体。这段设计意图被明确写在 CorsConfig 的类注释里。

原理 2 · 存储选型：一种数据一种存储

系统刻意使用了 4 种存储，每种都对应一类明确的数据特征 —— 这是「按访问模式选型」而非「有什么用什么」。

存储承载数据选型理由
MySQL 8.0 用户、角色权限、笔记元数据、频道话题、点赞收藏、计数、关注粉丝 需要事务、唯一约束、二级索引与多条件查询的数据。 关注幂等靠唯一索引实现，关系双写靠事务保证，这些能力其他存储给不了。
Redis 7.2 验证码、登录态、笔记详情缓存、用户信息缓存、关注/粉丝 ZSET 需要高并发读写、TTL、原子脚本、有序集合的场景。 ZSET 天然支持「按关注时间排序 + 分页 + 计数（ZCARD）」，用 MySQL 实现这三件事代价高得多。
Cassandra 笔记正文 note_content(id uuid, content) 正文是大文本、单键点查、无复杂条件、写多读多。 宽表 + 一致性哈希让它可以线性扩容，且写入无锁、无 JOIN，非常适合这种纯 KV 访问模式。 只有 id 一个查询入口，也说明它被设计成「按 UUID 取正文」的专用存储。
MinIO / OSS 图片、视频等二进制文件 非结构化大文件不适合进数据库或走应用进程， 用对象存储 + HTTP 直链访问，配合策略模式屏蔽厂商差异。

原理 3 · 缓存：多级、三防、可失效

多级缓存

Caffeine（进程内，纳秒级，容量 10000，写后 1 小时过期）→ Redis（跨实例共享）→ MySQL。 设计意图是让绝大多数详情页请求在本地内存就结束， 代价是引入了一致性问题，因此必须配合失效机制（见下）。

三防

  • 穿透：查不到时写 "null" 占位，60 + 随机 60 秒过期。
  • 雪崩：过期时间统一加随机量（1 天 + 随机 0~1 天），打散失效时刻。
  • 击穿：Caffeine 与 Redis 两级命中率高，数据库压力被大幅削减； 进一步可加互斥锁，当前实现未做。

可失效：延迟双删

写操作后通过 RocketMQ 延迟消息（延迟级别 1 ≈ 1s）清理 Redis 与本地缓存： Redis 用一条消息，本地缓存用广播消息让所有实例各自清理。 延迟的意义是「等在途读请求的脏回填落地后再删」，最小化不一致窗口。

用户信息缓存：批量 + pipeline 回写

UserServiceImpl.findByIds 体现了另一种缓存模式 —— 批量读 + 增量补 + 异步回写： 先用 multiGet 批量查 Redis，过滤空值；若全部命中直接返回； 否则只把没命中的 ID 在数据库查询，然后用 executePipelined 异步写回 Redis（带随机过期）。 这在「关注列表要一次补齐 10 个用户昵称头像」的场景下，把 10 次往返压成 2 次。

原理 4 · 分布式 ID：两种策略各司其职

号段模式（Leaf Segment）

用于 mybook_id 与 user_id。核心是 批量取号 + 内存发号：一次从 leaf_alloc 取走 step=2000 个 ID 放在内存里， 之后 2000 次发号完全不碰数据库。

双 buffer 是它的关键设计（SegmentBuffer）：

  • 内部持有两个 Segment，一个在服役、一个待命，currentPos 标记当前段。
  • 当前段消耗到一定比例时，后台线程（UpdateThreadFactory 创建的独立线程） 异步加载下一段到待命 buffer，nextReady 置位。
  • 当前段用完时若下一段已就绪，则瞬间切换，不等数据库 —— 这是它比「用完再取」方案吞吐高的根本原因。
  • 支持动态调整 step：以 15 分钟（SEGMENT_DURATION）为窗口、上限 MAX_STEP = 1000000， 按消耗速度自动伸缩；minStep 不小于数据库配置值。
  • 每分钟有一轮 updateCacheFromDb，把数据库新增的 biz_tag 灌进 cache、 已删除的从 cache 移除，因此新增业务标识不需要重启服务。

雪花模式（Snowflake）

用于笔记 ID：distributedIdGeneratorRpcService.getSnowflakeId()。

  • 完全无状态，不依赖数据库，不会成为写瓶颈，适合笔记这种量的数据。
  • 趋势递增：作为主键对 InnoDB 聚簇索引友好， 比 UUID 随机主键导致的页分裂要健康得多。
  • workerId 由 ZooKeeper 分配（leaf.snowflake.zk.address=127.0.0.1:2181）， 解决多实例 workerId 冲突问题。

为什么不全用一种

mybook_id 是用户可见、可运营的标识（长度 15，可从 10100 起步）， 需要按业务定制起始值 —— 这只有号段模式（依赖数据库里的 max_id）才能做到； 而笔记 ID 用户不可见、只求高并发不重复，雪花更合适。把 ID 当作业务属性来选型，而不是技术喜好。

原理 5 · 异步化：RocketMQ 的三种用法

① 异步落库（写扩散）

关注操作先写 Redis 立即返回，数据库更新交给消费者。 用户感知延迟从「两次 insert + 事务」降到「一次 ZADD」。 用最终一致性换取响应速度 —— 这是社交产品里最典型的取舍。

② 延迟消息（缓存双删）

DelayDeleteNoteRedisCacheTopic 使用 RocketMQ 延迟级别控制「1 秒后再删」， 避免自行实现延迟队列（时间轮 / 定时任务）带来的复杂度与可靠性问题。

③ 广播失效（本地缓存）

DeleteNoteLocalCacheTopic 用于通知所有实例清理各自的 Caffeine 缓存 —— 这是进程内缓存在分布式环境下唯一可行的失效手段。

原理 6 · 一致性与幂等：把约束下沉到存储

场景手段说明
关注 / 取关两表双写 TransactionTemplate 编程式事务 转发 A → B 的两条记录必须同时成立，任一失败即 setRollbackOnly()
消息重复投递 数据库唯一索引 uk_user_id_following_user_id；把幂等交给数据库，而不是在应用层做「先查再插」 （后者在并发下有竞态）
点赞 / 收藏重复操作 唯一索引 + status 位 uk_user_id_note_id 保证一人一行，重复点赞只更新状态，不新增行
Redis 与数据库不一致 以数据库为准 + 重建 关注列表 ZSET 未命中即从 t_following 全量重建； 粉丝 ZSET 不存在时消费者跳过，等读路径重建
正文写入后元数据失败 补偿删除 发布流程 catch 中调用 deleteNoteContent 回收孤儿正文（Saga 式补偿思路）

原理 7 · 配置外部化与运行时热更新

可调参数一律外置到 Nacos，并对「希望不重启就生效」的配置加 @RefreshScope：

限流阈值

mq-consumer.follow-unfollow.rate-limit: 1 → FollowUnfollowMqConsumerRateLimitConfig（@RefreshScope） 构造 Guava RateLimiter。大促时可在 Nacos 直接调大消费速率。

存储后端

storage.type: minio | aliyun → FileStrategyFactory（@RefreshScope）， 切换对象存储无需重新发版。

跨域白名单

mybook.cors.allowed-origin-patterns 默认 *， 生产环境应收窄为具体域名（用 Pattern 写法如 https://app.example.com）。

07关键设计点（代码级）

挑选 5 处「看起来简单、实际有讲究」的实现细节展开。

7.1 用 Lua 脚本把「校验 + 写入」变成一次原子操作

关注接口需要判断三件事（ZSET 是否存在、是否超 1000 上限、是否已关注）后再写入。 如果分成多条命令，并发下会出现「查完没超限、写入时已超限」或重复关注。 Redis 单线程执行 Lua，天然是原子的 —— 这是防并发竞态最直接的手段。

脚本返回码用途与触发场景
follow_check_and_add.lua -1 / -2 / -3 / 0 关注主链路。ZSET 不存在返回 -1（触发冷启动回填）；已达 1000 返回 -2；已关注返回 -3； 成功 ZADD 返回 0。Java 侧 checkLuaScriptResult() 统一翻译为业务异常。
follow_batch_add_and_expire.lua 0 冷启动 / 回填。把 ARGV 按「分数, 值」成对组装成 ZADD 参数批量写入， 末尾参数作为 EXPIRE。一次往返完成 N 条记录回填 + 过期设置。
follow_check_and_update_fans_zset.lua -1 / 0 被关注者粉丝列表。ZSET 不存在（-1）就跳过 —— 避免为每个用户都维护粉丝 ZSET 导致内存爆炸；存在时若超 5000 先 ZPOPMIN 淘汰最早粉丝再 ZADD。

值得注意的实现细节

  • 脚本资源按需加载：每次调用都 new DefaultRedisScript + ResourceScriptSource， 语义清晰但有开销。生产上更常见的是把 DefaultRedisScript 做成单例 bean（或直接传脚本文本， 走 EVALSHA 缓存），可减少 IO。
  • 时间戳入参：DateUtils.localDateTime2Timestamp(now) 作为 ZSET 的 score， 这样「按关注时间排序」直接由 Redis 的分数排序能力提供，不需要额外排序字段。
  • Collections.singletonList 的用意：代码注释明确写了「高并发场景下避免创建多余数组」， 单 key 脚本用 singletonList 而非 Arrays.asList，省一次对象分配。

7.2 线程池：参数是算出来的，不是拍出来的

三处线程池配置对比

  • 代码注释中保留了推导过程：CPU 密集型 core = N + 1，IO 密集型 core = N × 2。
  • 「max = core + 1，多加的 1 为有效磁盘数」—— 因为队列容量给到 200， 队列大时 max 设大反而增加线程切换成本而无收益（任务先进队列，队列满了才会扩到 max）。
  • 拒绝策略统一 CallerRunsPolicy：队列满时由提交任务的线程自己执行， 形成天然的背压，让上游变慢而不是直接丢任务。相比 AbortPolicy 抛异常丢数据，这是更稳的选择。
  • 优雅停机：setWaitForTasksToCompleteOnShutdown(true) + setAwaitTerminationSeconds(60)，发布时不丢在途的缓存回填任务。

本地缓存参数

Caffeine.newBuilder()
  .initialCapacity(10000)   // 预分配，减少扩容
  .maximumSize(10000)       // 容量上限，防 OOM
  .expireAfterWrite(1, HOURS) // 写后 1 小时过期
  .build();

maximumSize 是本地缓存的安全阀：进程内缓存没有 TTL 兜底就是内存泄漏。 这里用「容量 + 写后过期」双保险，再叠加 MQ 广播主动失效。 注意：expireAfterWrite 意味着热点数据也会在 1 小时后失效并回源一次， 这是「确定性」优于「最优命中率」的取舍。

为什么 starter 里要手动注册过滤器

ContextAutoConfiguration 用 FilterRegistrationBean 显式注册 HeaderUserId2ContextFilter，而不是直接给 Filter 加 @Component。 原因是 starter 里的类不由业务服务扫描（包路径不同），必须显式声明； 同时 FilterRegistrationBean 可以控制 urlPatterns 与 order， 比裸 @Component 更可控。这是 starter 与普通业务组件的关键区别。

7.4 网关过滤器顺序：@Order(-90) 的含义

AddUserId2HeaderFilter 标注 @Order(-90)，属于靠前执行的全局过滤器。 它必须在路由转发（默认 order 较大的 NettyRoutingFilter）之前完成， 否则 userId 请求头根本来不及加进请求。

一处需要留意的实现

try {
    userId = StpUtil.getLoginIdAsLong();
} catch (Exception e) {
    chain.filter(exchange);   // ← 未 return
}
Long finalUserId = userId;    // 未登录时仍是 null
... .header(USER_ID, String.valueOf(finalUserId))  // 写入 "null" 字符串
return chain.filter(newExchange);

未登录分支调用 chain.filter(exchange) 后没有 return， 过滤器会继续往下走并执行一次 chain.filter(newExchange)， 导致请求被转发两次（且第二次会写入字符串 "null" 的 userId 头）。 由于网关已由 Sa-Token 拦截未登录请求，这条分支实际很难触发，但仍是应该修掉的缺陷。

7.5 契约设计：为什么所有接口都是 POST

现状

对外接口清一色 @PostMapping + @RequestBody， 包括语义上明显是查询的 /note/detail、/relation/following/list。

这么做的合理性

  • 参数体统一：查询也会携带登录人、分页、过滤条件等结构化参数， JSON body 比 query string 更易扩展且无需 URL 编码烦恼。
  • 避免 URL 泄露：手机号、笔记 ID 等不出现在访问日志与浏览器历史里。
  • Feign 契约一致：内外部接口形态相同，减少认知负担。

代价与建议

  • 无法利用 HTTP 缓存：POST 默认不可缓存，浏览器与 CDN 层都帮不上忙， 所有缓存压力都落在应用层的 Caffeine/Redis 上。
  • 语义不清晰：幂等性无法从方法判断，客户端重试策略只能靠约定。
  • 建议：查询类接口改为 GET（分页/过滤走 query 参数）， 写操作保持 POST/PUT/DELETE；若担心 URL 泄露，可改为把敏感参数放 header。

08工程化与规约

依赖治理：${revision} + flatten 插件

问题

根 pom.xml 用 ${revision} 统一版本号（1.0.0）， 但子模块被单独安装 / 被其他项目依赖时，flatten-maven-plugin 不生效就会 解析不到 ${revision}，报「无法解析版本号」。

方案

  • flatten-maven-plugin，flattenMode = resolveCiFriendliesOnly， 在 process-resources 阶段把 ${revision} 展开成真实版本并写入 .flattened-pom.xml（仓库根目录可见该文件）。
  • 代价是生成物不自动清理，需清理时在 clean 阶段执行 flatten.clean。

根 pom 的两种治理手段

  • 统一版本变量：近 40 个依赖版本全部集中在 <properties> （sa-token.version、rocketmq.version、mybatisplus.version …）， 升级只改一处。
  • 统一依赖管理：所有自研模块（含 -api、starter）在 <dependencyManagement> 中声明版本，业务模块引依赖不写版本号， 避免多模块版本漂移。
  • 插件统一：spring-boot-maven-plugin（repackage 打成可执行 jar）、 maven-compiler-plugin（含 Lombok 注解处理器路径）、 mybatis-generator-maven-plugin（代码生成）都在 pluginManagement 中收口。

运维脚本：scripts/run.sh

一个 10KB 的 Bash 脚本把「编译 → 启动 → 停止 → 看日志 → 看状态」全部封装， 模块名支持短名（user）与全名（mybook-user）两种写法。 

scripts/run.sh                       # 帮助 + 各服务状态
scripts/run.sh status                # 查看运行状态
scripts/run.sh user                  # 默认动作 restart：编译 + 启动
scripts/run.sh restart all           # 全部重新编译并启动
scripts/run.sh build user            # 只编译（含依赖模块）
scripts/run.sh log user              # 跟踪日志
scripts/run.sh clean user            # 清理 target
scripts/run.sh -n restart user       # dry-run，只打印命令
scripts/run.sh user -- --server.port=8084   # 追加 Spring 启动参数

支持 JAVA_BIN / JAVA_HOME / JVM_OPTS / APP_ARGS / MVN_FLAGS / WITH_TESTS / DRY_RUN 等环境变量； 默认跳过单元测试（WITH_TESTS=1 才执行），并把日志统一收拢到 logs/ 目录。 把「开发环境怎么跑起来」也当作代码来维护，这是这个仓库做得比较扎实的一点。

其他工程实践

SQL 版本化

sqls/ddl.sql（建表）、drop.sql（清理）、 insert.sql（初始化数据）三件套，便于重建环境。

代码生成

user / note / user-relation 模块各有 generatorConfig.xml，用 MyBatis Generator 从表结构生成 DO 与 Mapper XML，保证字段映射不出错。

日志规范

各服务统一 logback-spring.xml；关键链路日志带 ==> / ## 前缀，便于 grep 定位。

压测资产

test/login.jmx（JMeter）与 test/test_login.ps1， 以及若干接口响应的截图留档。

09演进建议

以下条目来自对代码的逐处核对，按「缺陷 → 未完成 → 待补齐能力」三档列出， 每条都标注了位置，便于直接跟进。

已确认的逻辑缺陷

位置影响说明与建议
NoteServiceImpl.updateNoteIsTop() 功能错误 置顶接口实际调用的是 noteDOMapper.updateVisibleOnlyMe(noteDO)， 且构建 NoteDO 时设置的是 visible = PRIVATE、完全没有用到 updateNoteTopReqVO 的 top 值。 结果：调用「置顶」会把笔记改成「仅自己可见」，且不影响 is_top。 应改为读取 top 参数并调用更新 is_top 的 mapper 方法。
gateway AddUserId2HeaderFilter 潜在缺陷 未登录分支 chain.filter(exchange) 后缺少 return， 会继续执行到方法末尾的第二次 chain.filter(newExchange)，导致重复转发， 并在已放行的请求上写入字符串 "null" 的 userId 头。 建议补 return，并把 userId 为 null 时不加请求头作为处理逻辑。
note/config/ThreadPoolConfig.java 配置未生效 该类没有 @Configuration，方法也没有 @Bean， 全仓库无任何引用。而 NoteServiceImpl 通过 @Resource(name = "taskExecutor") 强依赖该 bean。 这意味着线程池参数（core 16 / max 50 / 队列 200）并未按此文件生效， 真实 bean 来源需要确认（对比 auth 与 user-relation 两个已正确标注的同类配置）。 建议补齐注解并确认 bean 唯一性。
AuthServiceImpl.loginAndRegister 代码异味 同一方法里用 switch 混合了验证码登录与密码登录两套流程， 且错误处理不一致（参数问题返回 Response.fail，校验失败抛异常）， 代码内的注释也标注了这处困惑。建议拆为两个策略实现，错误处理口径统一。
